# N01/N02: постановка и исследование новостного архива

**Статус: команды реализованы и проверены локально.** 36 поведенческих тестов
в Docker Python 3.11 проверяют постановку, поиск, финализацию, отрицательные
входы, различие публикаций/событий и конкурентное сохранение. Основные операции
и найденные дефекты прошли RED → GREEN. Production-прогон N01/N02 остаётся
отдельной приёмкой: сбой production Container-Use не засчитан как запуск теста.

Python 3.11+, стандартная библиотека. В AppFactory команды исполняются через
Container-Use проекта; локальные проверки выполняются в Docker.
GenericAgent определяет смысл, категории, события и замечания;
команды проверяют происхождение, фильтруют даты и текст, сохраняют JSON и считают
числа. Разметка `evaluation/` не входит в доставку или контекст агентов.

```sh
python3 /workdir/ipr4-news/news_commands.py \
  --inputs /workdir/ipr4-news/inputs \
  --results /workdir/ipr4-news/results /workdir/request.json
```

stdout: `{status:"ok",context:{...},data:{...}}`, exit 0. Ошибка:
`{status:"error",context:{...},error:{code,message,...}}`, exit 1.
Журнал начала, проверки входов, решений поиска и завершения идёт в stderr.

Все запросы содержат реальные ID проекта/запуска и следующие поля:

```json
{
  "operation": "prepare_brief",
  "project_id": "project-id",
  "run_id": "run-id",
  "corpus_id": "ipr4-news-tn416",
  "corpus_version": "1.0.0",
  "manifest": "news/manifest.json",
  "terminology": {
    "manifest": "terminology/manifest.json",
    "corpus_id": "ipr4-terminology",
    "corpus_version": "1.0.0"
  }
}
```

`manifest` разрешается относительно `--inputs`; файлы manifest — относительно
самого manifest. Все checksum проверяются перед операцией. Входы и результаты
должны находиться в разных корнях. `reference.path` относительно `--results`,
при чтении обязательно передавать и `path`, и `sha256`. Проверка checksum и
разбор публикаций, словарей и сохранённых результатов используют одни байты.
Чужой project/run,
изменённый файл, другой тип результата (`kind`) или входной manifest отклоняются.
JSON публикуется атомарно: готовый временный файл связывается с неизменяемым
путём без перезаписи. Одновременные одинаковые записи возвращают один reference.

## prepare_brief

Дополнительное поле `brief`:

```json
{
  "version": "1",
  "query": "Исследуй загруженный архив по согласованной теме",
  "topic": "Цифровая оптимизация разработки и добычи",
  "period": {"start": "2025-03-12", "end": "2026-03-02"},
  "inclusions": ["Задачи, методы и описанные применения"],
  "exclusions": ["Документооборот", "Переработка"],
  "output_formats": ["json"],
  "source_policy": "Сохранённый текст архива; сайты заново не прочитаны"
}
```

Версия — непустой простой ID. Период включительный по `published_date`;
даты событий и годы из заголовков его не заменяют. Список исключений может
быть пустым; включения и форматы непустые. Команда добавляет фактический период
архива, число публикаций, контекст и версии/checksum входов, затем сохраняет
`<project>/<run>/brief-<version>.json`. Выход `data={brief,reference}`.
Одинаковый повтор возвращает тот же файл; изменение требует новой версии.

Карточка штатного согласования показывает этот `brief` и `reference`.
Уточнение через Chat создаёт следующую версию. После подтверждения native gate
сохраняет фактический снимок решения в защищённый `workflow_approval` до перехода
к следующей фазе. Скрипт не аутентифицирует человека:
доступ к следующей фазе ограничивает workflow; receipt связывает её с файлом.

## candidates

Дополнительные поля:

```json
{
  "brief_ref": {"path": "project-id/run-id/brief-1.json", "sha256": "sha256-from-prepare"},
  "approval": {
    "approval_id": "actual-native-approval-id",
    "gate_node_id": "approve_news_brief",
    "brief_sha256": "sha256-from-prepare"
  },
  "terminology_result": {
    "query": "Исследуй загруженный архив по согласованной теме",
    "dictionary_versions": {"terms": "1.0.0", "taxonomy": "1.0.0"},
    "detected_terms": [],
    "expansions": [],
    "exclusions": [],
    "refined_query": "Уточнённая терминологом формулировка",
    "constraints": [],
    "ambiguities": []
  }
}
```

`terminology_result` соответствует B03 prompt. Query должен совпасть с
согласованным `brief.query`, версии и ID — с загруженными справочниками.
Поиск использует исходный query и явные expansions, без обхода related_ids
или автоматического словарного присвоения категорий. Лексический индекс содержит
publication_id, заголовок и полный сохранённый текст: явно названные номера
публикаций не нужно выдавать за термины предметного словаря. Нормализация Unicode,
регистра и пробелов применяется только для поиска; исходный текст сохраняется.
Совпадением считается полная нормализованная фраза либо общий целый токен длиной
от трёх символов. Автоматической морфологии нет; расширения и грамматические
варианты задаёт терминолог. Это отбор кандидатов, не классификация релевантности.

Выход содержит `candidates` с полным текстом, метаданными и `matches`, `audit`
для каждой публикации (`candidate`, `exclude_period`, `no_match`,
`insufficient_evidence`),
`exact_duplicate_groups`, `brief_ref`, `terminology_result`, `reference`.
Сохранённый JSON также содержит approval и проверенные входы. Ошибка чтения
не становится пустым результатом. Если файл прочитан, но `text`, `url` или
`source` отсутствует, равен null или пуст, публикация получает
`insufficient_evidence` и не поддерживает посчитанные события. Отсутствующий
файл и некорректный JSON остаются структурированными ошибками. При пустом
периоде кандидатов ноль и явно указана фактическая граница архива.

## finalize

Дополнительные поля: `candidates_ref`, `initial_analysis`, `analysis`, `critique`.
`candidates_ref` — reference результата candidates. Initial analysis — исходный
ответ исследователя, analysis — принятый вариант после максимум одной правки.
Оба сохраняются с вычисленными checksum; GenericAgent не вычисляет их вручную.

Структура analysis:

```json
{
  "publications": [{
    "publication_id": "actual-source-id",
    "decision": "include",
    "reason": "Основание по определению и исходному тексту",
    "categories": ["water-injection"],
    "evidence": [{"quote": "Точная подстрока исходного text"}],
    "limitations": ["Не приведён первичный протокол испытаний"]
  }],
  "events": [{
    "event_id": "researcher-event-1",
    "description": "Самостоятельный сюжет",
    "technology": "Метод, установленный по источнику",
    "task": "Решаемая задача",
    "object": null,
    "time": null,
    "evidence_level": "statement",
    "categories": ["water-injection"],
    "publication_ids": ["actual-source-id"],
    "evidence": [{"publication_id": "actual-source-id", "quote": "Точная подстрока исходного text"}],
    "merge_reason": "Одна публикация; сопоставление не требовалось",
    "limitations": []
  }]
}
```

Каждый кандидат имеет ровно одно решение:
`include`, `exclude`, `review`, `insufficient_evidence`. Только включённые
публикации поддерживают посчитанные события. Для include обязательны массив
categories, цитата и хотя бы одно событие. Если категория публикации или события
не установлена по словарю, categories=[] требует непустого limitations с
объяснением. Такие элементы считаются отдельно в uncategorized_publication_count
и uncategorized_event_count; выдумывать технологическую категорию для анонса
конференции не требуется. Review/insufficient сохраняются для читателя,
но не входят в итоговый набор событий. Фрагментарную тематическую публикацию
можно включить с ограничениями и уровнем statement/not_established.

Уровни: `statement`, `laboratory`, `field`, `operational`, `not_established`.
Разные события одной публикации имеют разные ID; одному событию могут
соответствовать несколько публикаций. Для каждого источника события нужна
собственная цитата. При объединении требуется `merge_reason` по объекту,
содержанию и времени. Сходство заголовков или общее слово недостаточны.
`object`/`time` — строка либо null, неизвестные значения не восстанавливаются.
Содержание меню и соседних новостей не становится событием основной статьи.

Если цитата публикации содержит собственный publication_id, он должен совпасть
с ID этой публикации. Точный клон события с новым event_id отклоняется, чтобы
не удваивать число событий. Смысловое тождество разных описаний проверяет критик.

Критика:

```json
{
  "correction_cycle": 1,
  "notes": [{
    "id": "review-1",
    "publication_ids": ["actual-source-id"],
    "event_ids": ["researcher-event-1"],
    "issue": "Что не следует из исходника",
    "action": "Как исправить вывод",
    "resolution": "resolved",
    "resolution_reason": "Как изменён принятый вариант"
  }]
}
```

Допускаются 0 или 1 цикл, список notes может быть пустым. Критик сначала
фиксирует реальные замечания; correction один раз обновляет analysis и статусы
`resolved`/`unresolved` с объяснением. Неразрешённые замечания сохраняются явно.

Команда проверяет итоговые ID, цитаты и связи и вычисляет публикации, события,
распределения категорий/доказанности, источники и дубли. `statistics` содержит
`publication_count`, `event_count`, `candidate_count`, `archive_publication_count`,
`decisions`, `categories` с отдельными publication_count/event_count,
`evidence_levels`, `source_count` (длина списка источников URL/издатель) и
`publisher_count` (число разных издателей). Заявления входят в число событий
со своим evidence_level; число событий не означает число доказанных внедрений.
Сохраняет неизменяемый
`<project>/<run>/news-result.json`. Выход `data={result,reference}`. При другом
результате нужен новый run; существующий файл не перезаписывается.
Агент регистрирует JSON штатным `create` с теми же байтами/содержимым и сверяет
его доступность в Artifacts. HTML/CSV/PDF относятся к N04/B05.

## Локальная проверка

По явному разрешению пользователя тесты выполняются также в локальном Docker
с read-only подключением пакета. Временные входы и результаты тестов находятся
в контейнере. Команда внутри контейнера:

```sh
python -m unittest discover -s tests -p 'test_news*.py' -v
```

Тесты не обращаются к LLM, Bifrost, MongoDB и production. Они проверяют команды;
нативное согласование и качество решений GenericAgent требуют отдельных
интеграционных/смысловых свидетельств. Контрольная разметка остаётся вне runtime.
